# 把渗透测试当作一场不完全信息博弈

## 灵眼的设计哲学

一份扫描报告最容易被误读的地方，是它看起来像一张“完成清单”：扫了多少主机、命中了多少规则、高危有多少个。但真正决定测试质量的，往往不是清单长度，而是另一个问题：

**下一步做什么实验，最能改变我现在的判断？**

这个问题没法靠增加扫描器回答。它要求我们把测试过程本身当成一个带有信念、观测、成本和对手的决策过程。灵眼就是围绕这个想法做出来的：一个在 DeepSeek Harness 里运行的授权安全测试模式，用探索图记录信念，用意图表示实验，用证据约束结论。

这篇文章讲它的设计哲学，以及这些哲学怎样落到具体的数据结构和工具语义里。它不试图证明这套方法一定优于别的做法，只是把我们在实现过程中想清楚的东西写下来。

## 一、我们面对的不是系统，是信念

如果把目标系统看成一个确定的状态机，渗透测试就退化成“遍历未知分支”：只要有足够时间，所有分支都会被走完。但真实情况不是这样。

我们看不到完整状态。我们看到的是响应、报错、时序、页面差异、文件内容、版本号，以及运维和历史留下的残迹。这些观测共同支撑一个**信念**：哪些资产存在、哪些路径可达、哪些输入被怎样处理、哪些结论只是猜测。

更麻烦的是，目标会响应、会隐藏、会变化。一个今天返回 404 的路径，可能在换了 Host 头之后返回 200；一个被过滤器拦下的 payload，可能在另一层解码后生效；一次失败可能意味着“不存在”，也可能意味着“存在但被挡住”。所以渗透测试更接近**不完全信息博弈**，而不是一次静态扫描。

在这个框架里，动作也不只分“侦察”和“利用”两类。一次利用首先是实验：它产生观测，观测更新信念；一次看似没有收益的尝试，可能排除掉一整条错误假设。反过来，一次“成功”如果拿不到可复现证据，也只是把不确定性换了个位置。

灵眼的第一个设计决定，就是不再把“事实”当成真相，而是当成**信念的更新算子**。每条事实都有 basis、confidence 和 provenance：

- `observed`：直接观测到；
- `inferred`：从观测推导出来；
- `assumed`：当前假设，还没有验证；
- `negative`：查过、被挡住或不存在，并记录原因。

否定结论和假设都保留，不因为“不好看”而丢掉。矛盾也不急着覆盖：冲突本身往往就是最有价值的信息。

## 二、DAG-MDP：图不是画给人看的

探索图常被画成一张漂亮的拓扑图，但在灵眼里，它首先是决策结构。

节点是目标、意图、事实和漏洞；边是前置关系：这个意图依赖哪些事实，这个发现又由哪次实验产生。意图不是待办事项，而是**实验**：它写清预期观测，执行后要么把假设升级为事实，要么留下否定证据。于是“下一步能做什么”不再由时间决定，而由前置事实是否满足决定。

这接近一个基于 DAG 的马尔可夫决策过程：状态是信念，动作是可用实验，转移由观测完成，奖励是向目标推进的信息增益，成本是时间、token、暴露面和风险，约束是动作掩码，授权范围是状态空间边界。

这里需要诚实一点：它不是严格的 POMDP。真实系统里还有隐藏状态、非平稳行为和观测噪声，我们的图也做不到完备。把它叫 DAG-MDP，是因为这个建模足够解释“为什么下一步该做这个实验”，而不是宣称数学上已经闭合。

在这个近似下，排序就有了依据：优先选择“最可能改变计划”的实验，而不是平铺覆盖。一次能区分两种假设的探测，价值高于十次重复确认；一次失败如果能排除一条路径，也应当被记录和利用。

停止条件同样来自收益比较：当边际信息增益低于成本，或者目标已经被证明或证伪，测试就该收手。而不是等清单跑完。

## 三、四条经验，四个字段

哲学如果只停在文章里，就会变成口号。灵眼做的另一件事，是把四条安全经验变成数据结构。

### 1. 源码可得性取决于残留，不取决于站点质量

能不能拿到源码，经常不取决于站点写得好不好，而取决于运维当时顺手删了什么：`.git` 目录、备份文件、source map、调试端点、CI 产物、错误页、注释、旧版本，以及代码托管平台上的历史泄露。

这类信息没有“扫描规则”可套，它是一种侦察动作。灵眼把源码获取当作一等信息动作，证据记录获取途径、残留类型和可信度；报告单独写“信息残留”，而不是把它归为运气。

### 2. 净化发生在入口，危险点在每一次拼接

入口过滤不等于存储安全。同一个输入在“接收、规范化、存储、拼接、解释器”的每一步都可能被不同规则理解；真正危险的是拼接点处的解释上下文。

所以灵眼记录数据流：source、transform、sink。sink 注明解释器、编码和上下文，漏洞关联到具体拼接点，而不是笼统写一句“存在注入”。注入的信道选择，本质上是“对方愿意告诉我什么”的观测通道选择：先探测报错、布尔、时间、带外哪条信道可行，再按噪声和成本挑一条，证据记录 channel。

### 3. 双层解码：不是猜黑名单，是让两层理解不一致

过滤器解码一次，运行时又解码一次。目标不是猜中过滤器黑名单，而是构造一种输入：第一层解出来的东西仍然“看起来干净”，第二层解出来才是有效载荷。

灵眼用证据的 layers 记录每一层期望的规范化、解码、字符集和截断规则，用差分响应验证层间差异。重点不是“哪个字符被拦了”，而是“两层对同一串字节的理解在哪里分叉”。

### 4. token 里的元数据不是可信输入

JWT 的 header 和 payload、cookie 属性、OAuth 参数、SAML 断言、路径参数里的“签名过的元数据”，都可能被下游当成事实使用。信任边界错误的本质，是“谁断言、谁验证、验证了什么”没有对齐。

灵眼要求任何 token 或断言类测试先写 trustBoundary：断言来源、验证方、被信任的字段。没有这个说明的漏洞，在复核清单里会被标出来，而不是直接进报告。

## 四、把哲学写进产品

这些想法最后落成了一套比较克制的数据模型：目标、意图、事实、漏洞、资产、证据、数据流、提示、约束、复测。功能上它不追求“什么都有”，而是尽量让每个字段都能回答一个决策问题。

几个具体的设计选择：

**覆盖率按证据算，而不是按“碰过”算。** 一个资产只有被漏洞锚定，或被带证据的事实锚定，才算“已测”。这个规则是实测中逼出来的：早期 worker 提交了一条没有证据的 observed 事实，页签立刻显示覆盖率上升，但那条事实只是按指令填的文字。后来我们收紧了规则，宁可显示“未测”，也不给假信号。

**执行 agent 的提交要么有证据，要么标假设。** worker 通过 `ly_fetch` 读上下文，通过 `ly_submit` 写回结果；没有实际观测时，basis 必须写 assumed，不能声称 observed。协议里把这条写死，因为它直接决定报告可不可信。

**报告必须包含信念缺口。** 除了漏洞和资产，报告还列仍依赖的假设、否定证据、未测资产和未完成项。一份只写“发现了什么”的报告，会隐藏“还有什么不知道”。

**复测是独立记录。** 复测不覆盖原始漏洞，结论单独保存为 reproduced、fixed 或 inconclusive。这样报告能回答“这个问题现在还在不在”，而不是只回答“曾经有没有”。

**Web 页签展示的是信念，不是仪表盘。** 总览、探索、资产、漏洞、证据、数据流、报告、复测八个子页，围绕的是“现在相信什么、还缺什么”，而不是堆指标。

## 五、这套东西不保证什么

需要明确说清楚边界。

第一，排序是启发式的。信息增益没法精确计算，灵眼用的是依赖就绪、优先级、覆盖缺口和信念缺口的组合排序，不保证最优策略，只保证“比按清单扫更接近决策”。

第二，图模型有损。DAG 不适合表达所有隐藏状态和循环反馈，真实对手也可能主动制造噪声。模型有用，但不是真理。

第三，自动化有边界。灵眼有可选的宿主调度器，能按前沿自动派发执行子 agent；但当前版本每个 open 意图只自动派发一次，没有租约、心跳和两阶段收尾，复杂失败路径仍然需要指挥官介入。默认也是关闭的。

第四，授权和约束不是装饰。工具会把 allow/deny 约束注入提示词，并校验明显越界，但真正的执行边界仍由宿主的沙箱和审批负责；测试范围是使用者自己定的。

第五，证据可复现性依赖执行环境。同样的命令在不同机器、不同网络、不同时间可能给出不同结果；证据记录环境和通道，是为了让结论可复核，而不是假装它是永恒的。

## 结语

渗透测试的产出，最终不是一份漏洞列表，而是一个更接近真实的信念：哪些结论有证据，哪些只是假设，哪些路径被排除了，下一步做什么最值得。

把测试过程当成不完全信息博弈，把探索图当成 DAG-MDP，把每条事实当成信念更新，把每个字段都用来回答一个决策问题——这就是灵眼的设计哲学。它不新，也不神秘，只是要求我们别把“扫过了”当成“知道了”。
